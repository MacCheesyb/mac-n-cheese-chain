# R0NI Testnet — multi-node simulator

Prototype only — not audited, no real value, do not use for real funds.

## What this is — and what it is not

- **Simulated, not real VMs.** Three nodes run as separate OS processes
  on ONE Linux VM, each with its own data directory, talking over
  localhost HTTP (127.0.0.1:8001–8003). Docker was not available on
  this machine and no real VMs were created. Say so whenever you
  quote the numbers.
- **Mac's address is inbound only.** Mac's address is
  `R0NI-ebeb98a5aeea016f49e6abf1c8b1e492317a102d`. The testnet does
  NOT have his private key, never asked for it, and never signs a
  transaction from his address. Test transactions are: test wallet
  → Mac's address, and test wallet → test wallet (fully signed by
  the test wallets). A transaction *from* Mac's address requires
  Mac to sign it in his own wallet app — it is recorded as such
  in `analytics.json`, not simulated.
- **Test funds are test-only.** Genesis allocates 1,000,000 test
  R0NI to each of three freshly generated test wallets. Those keys
  live only in `/tmp` for the run and are never committed.

## Files

- `node.py` — the node: EvoHash-11 (imported from `roni_wallet.py`,
  the exact chain, not a reimplementation), PoW difficulty `0000`,
  mempool, Ed25519-signed transactions verified before acceptance,
  localhost P2P gossip (transactions + blocks), longest-valid-chain
  sync, JSON HTTP API (`/chain`, `/mempool`, `/status`,
  `/balance?address=…`, `POST /tx`, `POST /block`).
- `run_testnet.py` — starts 3 nodes, runs 20 phase-1 transactions,
  a 30-transaction TPS burst, a node-restart sync test, and four
  security tests, then writes `analytics.json` / `ANALYTICS.md`.
- `test_certs.py` — tests the asset certification / NFT layer
  (v0.3): mints PNG, document and audio certificates, verifies
  them, transfers one and verifies under the new owner, and
  tests the rejections (forged issuer signature, tampered
  asset, duplicate, non-owner transfer, expired) on the CLI,
  in a local registry, and on a live single node. Results in
  `cert_test_results.json` (21 checks, all passing).
- `genesis.json` — the testnet genesis block (generated per run;
  addresses only, no private keys).
- `analytics.json`, `ANALYTICS.md` — measured results from the run.

## Spending from Mac's genesis address — the only permitted path

The testnet never holds, asks for, or uses the genesis private key.
A transaction *from* Mac's address can only arrive as a signed
transaction he creates himself in his own wallet app:

1. Mac signs the transfer in standalone `wallet-app.html` (his key
   never leaves his device).
2. He provides the signed transaction JSON.
3. `testnet/accept_signed_tx.py signed-tx.json` verifies the
   signature against the sender's public key and submits it to a
   node, which re-verifies it before acceptance.

Recommended path: Mac makes **one** signed transfer in-app from
genesis to a fresh disposable test wallet (small amount). The
testnet then uses *that* disposable test wallet's keypair
(test-only, generated by the testnet) for further spending tests
— never the genesis key.

## Message / media payloads — transaction format v2

A transaction may carry an optional `"data"` payload, so a
transaction can include a message or media — a picture, song,
short video, GIF, or other digital file. This is what gives the
chain real utility beyond moving numbers around.

**Format** (see `roni_wallet.py` for the full spec and the reasons):

```json
{"kind": "text", "mime": "text/plain", "filename": "message.txt",
 "original_size": 157, "compressed_size": 157,
 "sha256_of_original": "<64 hex of the ORIGINAL bytes>",
 "compression": "none", "data_b64": "<base64 of the bytes>"}
```

Kinds: `text`, `image`, `audio`, `video`, `gif`, `other`, `ref`.
`ref` is an off-chain reference — only the SHA-256 and a URI go
on-chain (see below).

**Limits — why they exist:** a chain that stored every song and
video inline would bloat beyond what phones can sync, so storage
is bounded on purpose.

| Payload | Limit |
|---|---|
| Text message | 1,000 characters, stored uncompressed |
| Media (image / audio / video / gif / other) | 5 MB raw, compressed with zlib level 9, max 1 MB compressed on-chain |
| Off-chain reference (`ref`) | No size limit on the media (it is not stored on-chain) |

Anything over the inline limits is **rejected** with an error
telling the user to use a `ref` payload instead.

**Lossless delivery — how it is guaranteed:** the node
decompresses the payload and checks BOTH the SHA-256 of the
original bytes AND the decompressed size before accepting it,
and extraction re-checks the hash of the written file. What
comes out is byte-identical to what went in, or it is rejected
— never silently corrupted. The payload is also covered by the
transaction signature (a v2 transaction is signed over
`sender|recipient|amount|nonce|<sha256 of the canonical payload
JSON>`), so tampering with the payload breaks the signature and
the txid. Decompression is capped at the 5 MB raw limit, so a
small compressed bomb cannot expand into gigabytes of memory.
A MIME allowlist per kind rejects e.g. an "image" carrying
`text/plain`.

**Off-chain reference (`ref`):** for media over the inline
limits, or media you do not want replicated to every node.
Store only the SHA-256 + a URI (`http://`, `https://`,
`ipfs://`, `magnet:`) on-chain. The media itself is NOT
stored or delivered by the chain — whoever fetches it must
hash-check it against `sha256_of_original` before trusting it.

**Attach / extract (CLI):**

```bash
python3 roni_wallet.py payload-text "hello, chain"          # -> payload JSON
python3 roni_wallet.py payload-file photo.png                # kind/mime inferred
python3 roni_wallet.py payload-file song.mp3 --kind audio --mime audio/mpeg
python3 roni_wallet.py payload-ref https://example.com/song.mp3 audio/mpeg 12000000 <sha256-hex>
python3 roni_wallet.py validate-payload payload.json        # ok / reason
python3 roni_wallet.py make-tx wallet.json <password> <to> <amount> <nonce> payload.json
python3 roni_wallet.py extract tx.json out.png               # verifies SHA-256, writes original bytes
```

**Tests:** `testnet/test_payloads.py` (offline roundtrips +
rejections, plus a live single-node roundtrip) and the media
phase of `testnet/run_testnet.py` (results in
`testnet/payload_test_results.json` and `testnet/ANALYTICS.md`).
Roundtrips tested: text, PNG, GIF, WAV, and a real 1-second
ffmpeg MP4 — all extracted byte-identical, SHA-256 matching.
Rejections tested, all refused: oversize raw, oversize
compressed, corrupted compressed data, SHA-256 mismatch,
bad MIME, over-long text.

## Asset certifications / NFTs — transaction types cert-mint / cert-transfer

A certificate is a signed record that a real asset belongs to
an owner at a point in time, issued by someone — the basis for
NFTs and for certifying real-world assets and documents. It is
built on the v2 media payloads above: the asset file travels
in the transaction's `data` payload (inline or `ref`), and the
certificate records only its SHA-256.

**Certificate format** (see `roni_wallet.py`, "Certificates"):

```json
{"cert_id": "CERT-<40 hex of EvoHash-11(asset_sha256 + '|' + issuer)>",
 "asset_sha256": "<64 hex of the ORIGINAL file>",
 "asset_kind": "image|audio|video|gif|document|other",
 "asset_mime": "image/png", "asset_filename": "mustang.png",
 "description": "1967 Ford Mustang — photo",
 "issuer": "R0NI-<issuer address>", "issuer_pubkey_hex": "<64 hex>",
 "owner": "R0NI-<owner address>",
 "issued_at": 1795154815, "expires_at": null,
 "signature": "<Ed25519 signature over the canonical cert JSON>"}
```

**Rules the node enforces:**

- `cert-mint` (amount 0 — no R0NI moves, only the record):
  the issuer must be the transaction sender, the owner must
  be the recipient, the cert ID must derive from the asset
  hash + issuer, the issuer signature must verify, and the
  payload hash (if any) must match the certified asset.
  A mint of an already-certified asset + issuer is rejected.
- `cert-transfer` (amount 0): signed by the CURRENT owner
  only. The node checks the current owner from the chain
  before accepting it, and rejects a transfer by anyone else.
- Verification is by anyone: recompute the file's SHA-256,
  check the cert ID and the issuer signature, and check the
  current owner in the chain (`/certs`, `/cert?cert_id=…`).
  An expired certificate reports "expired" — authentic, but
  no longer current. Ownership lives in the chain, not in the
  certificate document, which always names the owner at mint.

**CLI:**

```bash
python3 roni_wallet.py cert-mint issuer.json <password> mustang.png <owner> "1967 Ford Mustang" 0 --registry certs.json
python3 roni_wallet.py cert-verify mint-tx.json mustang.png --registry certs.json
python3 roni_wallet.py cert-transfer owner.json <password> mint-tx.json <buyer> 0 --registry certs.json
```

**Tests:** `testnet/test_certs.py` (21 checks, all passing —
see `testnet/cert_test_results.json`).
